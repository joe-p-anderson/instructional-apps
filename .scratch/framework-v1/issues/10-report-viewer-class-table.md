# 10: Report Viewer: class table from a Brightspace zip

Spec: docs/specs/0001-framework-v1.md (vocabulary from GLOSSARY.md; respects ADRs 0001–0003).

**What to build:** The instructor drops the Brightspace bulk-download zip (or many Reports) onto the Report Viewer and sees the whole class in one table, with a detail page per student and scores recomputed from the Attempts.

**Blocked by:** 09

**Status:** resolved

- [x] A small zip reader, vendored or loaded from a pinned CDN version, reads the bulk download entirely in the browser
- [x] Each Report is matched to its uploader using the zip's folder and file names
- [x] Class table: name, Tasks passed, Attempts, points, and a flags column (populated by ticket 11)
- [x] Clicking a student opens their full detail (Attempts, State at each Attempt, answers, snapshots)
- [x] Scores recomputed from the Attempts rather than trusted from the Report's stored totals
- [x] Node tests with fixture Reports generated by the runner core, plus uploader names shaped like a Brightspace bulk download

## Comments

- Built on branch `ticket-10`. The zip reader is our own, with no dependencies (`framework/v1/report-viewer/zip.js`, `readZip`/`isZip`). It uses native `DecompressionStream('deflate-raw')` and handles the stored and deflate methods. ZIP64 and encrypted entries are refused. Nothing is vendored.
- Core (`report-viewer/core.js`) adds `uploaderFromPath`, `readSubmissions(files)` and `openClass(submissions) -> { rows, errors }`. Each row has name, uploader, sealedName, tasksPassed, taskCount, attemptCount, earned, possible, `flags: []` and `view`. Ticket 11 fills `flags`, and the UI renders them as `{ kind, label?, message? }`. Ticket 12's CSV reads `rows`.
- Brightspace naming is PROVISIONAL (not checked against a real download). It assumes `<id>-<id> - First Last - <date>` as a per-submission folder, or the same plus ` - <file>` as a flat file. The parsing lives only in `uploaderFromPath`. When a name doesn't match, the row uses the sealed name.
- Scores: `openReport` now rescores every Task from its own Attempts. A Task's points count if any Attempt's results contain no failure. A graded Question's points count once one of its results passed. A free-text Question's points count once it has a non-empty answer. Stored totals are kept only as `view.stored`.
- Format change (additive, still v1): the runner's Reports now record each Task's `points` and `questions: [{ id, graded, points }]`, which rescoring needs. Reports without them count all `possible` as the Task's own points.
- Also fixed a ticket-09 bug where State at each Attempt rendered as `[object HTMLSpanElement]`.
- Tests: `tests/unit/report-viewer/{scores,class-table}.test.js` (with the `make-zip.js` helper), `tests/e2e/report-viewer-class.spec.js`. `npm test` (98) and `npm run test:e2e` (29) pass.
- Merged branch `ticket-10` into `framework-v1` via a non-fast-forward merge commit. No conflicts. `npm test` (98) and `npm run test:e2e` (29) pass.
